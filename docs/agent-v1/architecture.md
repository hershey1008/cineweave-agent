# V1 技术架构

2026-10-22 更新：单轮编排已接入 LangGraph，推荐流水线与会话事务边界保留。实现、切换方法及对照证据见 [LangGraph 改造](langgraph-refactor.md)。

状态：2026-10-19 的设计基线。2026-10-20 本地实现、运行差异和实测结果分别见 [运行说明](../RUN_LOCAL.md) 与 [验收记录](../LOCAL_VALIDATION.md)。本文中的阈值仍为设计目标。

## 1. 目标与范围

实现支持多轮修改条件的电影推荐 Agent：自然语言理解、语义召回、个性化排序、硬条件过滤、推荐解释、会话反馈。

| 能力 | V1 行为 |
| --- | --- |
| 自然语言选片 | 将主题、氛围和其他需求转成语义查询与结构化条件 |
| 硬条件 | 类型包含/排除、年份范围、最大片长、排除指定电影、排除已交互电影 |
| 多轮修改 | 保留未修改字段，区分设置、清除和保留 |
| 指代替换 | 根据上轮展示顺序解析“第三部”，排除后重新推荐 |
| 个性化 | 复用 FunRec 用户历史、召回和 DeepFM 评分 |
| 解释 | 根据已查询事实与证据片段组织说明 |
| 条件不足、冲突或库外要求 | 澄清或说明无结果，提供调整建议 |
| 反馈 | 喜欢、不感兴趣、看过；作用于会话并记录日志 |

默认推荐 10 部，上限 20 部。“轻松”“烧脑”等是软语义偏好；“120 分钟以内”“排除 Horror”等是硬条件。缺片长的电影不能认定满足片长上限。“绝对没有血腥镜头”等缺少可靠标注的硬要求，需要澄清或明确无法验证。

V1 对话更新会话偏好；长期偏好沿用个人资料页。反馈不触发在线训练，也不自动写成原有评分。MovieLens-1M 目录较老，不能承诺推荐目录之外的新片。

Semantic ID 生成式召回、HSTU/SASRec 接入、偏好优化、实时增量索引和多 Agent 协作均为后续可选方向。

## 2. 基线与架构选择

已检查的 FunRec Web 链路：冷启动判断 → YouTubeDNN / I2I / 类型偏好多路召回 → Snake Merge → DeepFM → 类型/年代打散 → 元数据组装。

召回策略具有统一接口，服务已有多通道并发。当前 DeepFM 输入不包含对话意图；多个资源/业务服务采用单例。V1 将会话上下文作为请求参数传入，不通过临时修改单例配置实现个性化。

| 组件 | 方案与职责 |
| --- | --- |
| 前端 | Vue；新增对话页、条件标签、卡片与反馈 |
| 业务后端 | FastAPI；认证、Agent、状态管理与推荐编排 |
| LLM | 服务商可配置；结构化意图和解释措辞；具体型号部署前固定并登记 |
| 语义服务 | 独立 Python 环境；嵌入模型、向量加载与精确检索 |
| PostgreSQL | 电影/用户业务事实，会话、消息、事件和反馈 |
| Redis | 缓存、并发协调；不作为唯一会话来源 |
| Elasticsearch | 原有文本搜索、实体查询和相关候选能力 |

语义服务独立部署，隔离嵌入模型运行依赖与原 TensorFlow 2.15 环境。Compose 从五服务扩展到六服务。模型权重提前准备，服务就绪后接收请求。

## 3. 离线内容和索引

### 3.1 数据输入

使用 FunRec 扩充版 `movies.pkl` 和按需关联的 `movie_metadata.pkl`。原始 MovieLens-1M 不自带完整简介。当前数据检查情况见[来源与数据说明](../provenance.md)。

清洗顺序：统一 ID → 处理缺失和占位符 → 解码 HTML 实体 → 标准化字段 → 拼接文本 → 质量报告。

固定文本模板包含片名/原名、可靠别名、年份、类型、简介。保留原始字段；记录清洗结果和文档哈希。V1 优先使用已有英文简介，通过多语言模型匹配中文查询；是否翻译通过开发集验证。导演可后续加入，长演员列表不作为首版必需项。

类型、年份、片长另存为结构化元数据，执行硬过滤。简介缺失时使用片名和类型构建基础文本，并标记质量等级；不让 LLM 编造简介。

### 3.2 模型与检索

初始选型为 BGE-M3 dense embedding，1024 维。只启用稠密向量；电影向量和查询向量归一化，用内积实现余弦相似度。实际模型 revision、推理库、最大输入长度与归一化策略写入 manifest。

3883 × 1024 个 float32 约为 15 MiB；V1 使用 NumPy 全量精确检索。模型权重和运行内存另计，查询编码与矩阵检索分别测时。模型运行硬件部署前登记，CPU/GPU 性能不混报。

内部语义服务接收查询、合法 ID 集合和候选上限，返回候选、所需语义分数及索引版本。小目录下可一次返回合法目录的分数映射，供混合候选排序复用，避免同一轮重复编码。该内部结果不直接暴露到前端。

### 3.3 产物与发布

| 文件 | 内容 |
| --- | --- |
| `documents.jsonl` | 电影 ID、清洗文本、元数据和文档哈希 |
| `movie_ids.npy` | 向量行到电影 ID 的映射 |
| `embeddings.npy` | 归一化电影向量 |
| `manifest.json` | 数据哈希、模型 revision、模板版本、维度、构建时间 |
| `quality_report.json` | 缺失、重复、异常字段与向量质量报告 |

产物位于外部 processed data 的 `web_project/semantic_index/<version>/`，不进入 Git。完整构建、检查后原子切换活动版本，失败保留旧版。业务后端验证预期索引版本；不匹配时禁用语义通道并报告。

V1 按批次发布电影目录和索引，电影资料变更后重建并发布；不提供实时语义增量更新。最终返回前仍以业务库核对电影存在性和硬条件。

## 4. Agent 执行模型

采用有动作与步骤上限的工具型 Agent。外层状态机控制执行，模型只在允许的动作和工具契约内给出结构化决策。

1. 认证并读取会话快照、当前条件和上轮推荐顺序。
2. LLM 解析本轮输入，输出字段修改操作及动作。
3. 校验类型、取值和操作；解析电影名、别名、列表位置。
4. 执行受控工具，获取画像、候选和事实。
5. 检查空结果、冲突、字段缺失和目录范围。
6. 生成有证据的解释；失败回退模板。
7. 根据会话版本检查，原子保存消息、推荐记录与新状态。

动作：`recommend`、`replace`、`clarify`、`explain`、`no_results`。

工具：`resolve_movie`、`get_user_context`、`retrieve_candidates`、`get_movie_facts`。工具首先作为内部业务接口，不引入额外协议依赖。

### 4.1 执行预算与边界

- 通常两次 LLM 调用：意图解析、解释措辞；结构化结果无效时允许一次修复，总计最多三次。
- 每轮最多一次候选补检索，执行始终服从整体截止时间。
- 超时时，意图未可靠解析则返回可重试错误/澄清；不能用猜测条件生成结果。
- LLM 不生成 SQL、任意 URL、用户身份、电影事实或推荐 ID。
- 电影简介和用户内容均为业务资料，不能覆盖系统规则或工具权限。
- 用户身份由登录态提供，不交给模型选择。

### 4.2 会话修改

状态显式保存结构化条件；每轮输出区分“保留”“设置”“清除”。“时长不限了”只清除时长上限，保留排除恐怖片。“第三部”根据上轮保存的展示顺序解析，不能重新查询后猜测位置。

请求级状态不写入共享服务实例。并发时使用版本检查：旧版本响应不能覆盖新状态，返回可恢复的冲突结果；重复消息 ID 去重。

## 5. 推荐流水线

### 5.1 分支与召回

无语义需求的首页请求沿用原有行为。会话请求创建独立上下文：用户历史、语义查询、结构化硬条件、会话排除项、预算和策略配置。

| 通道 | 初始候选上限 |
| --- | ---: |
| 语义召回 | 100 |
| YouTubeDNN | 100 |
| I2I | 100 |
| 偏好类型 | 100 |

新用户使用“语义候选 + 原冷启动候选”，不因冷启动直接绕开语义通道。初始候选预算在开发集调整，测试集冻结配置。

### 5.2 融合与过滤

1. 根据业务库生成满足硬条件的合法 ID 集合，取完整用户交互集合执行排除已看。
2. 语义通道在合法集合中检索；原通道召回后执行同一过滤器。
3. 去重时保留全部来源、各通道分数和名次。
4. 采用 RRF 等名次融合，不直接相加不同量纲的原始分数。
5. 初始最多保留 200 个候选，为语义头部候选保留配额，避免早期融合完全挤出相关结果。
6. 候选不足时扩大检索深度；硬条件不自动放宽。

### 5.3 会话排序

对较大的保留候选集计算 DeepFM 与语义信号，然后综合排序。不能先由 DeepFM 截到最终 10 部再处理意图。

启动方案使用归一化名次分数：语义 0.6、DeepFM 0.3、召回融合 0.1。该权重是开发起点，使用开发集调优并记录。新用户不使用无有效个性化依据的 DeepFM 信号，改用语义与冷启动信号。

原类型/年代打散按请求复用，记录对相关性的影响并做消融。最终 `score` 为系统排序信号，不解释成真实点击概率；最终展示名次单独保存。

### 5.4 事实与解释

后端先确定证据：类型匹配、年份/片长条件、简介片段。LLM 只组织措辞，不改变电影列表、数值或来源。数值事实优先模板展示；简介解释附可审计证据。未支持的生成内容丢弃或回退模板。

## 6. 数据与服务职责

PostgreSQL 为会话事实来源；Redis 缓存可失效重建。会话、消息、事件、反馈分表保存，详情见[接口与状态契约](contracts.md)。新增表通过仅作用于这些表的增量脚本创建，禁止运行重置业务数据的导入流程。

“推荐已返回”和“前端实际展示”分开记录；实际曝光由前端卡片展示触发，点击、喜欢、不感兴趣、看过分别记录。反馈关联用户、会话、请求和电影，检查该电影确实属于相应推荐。

## 7. 失败和降级

| 故障 | 预期行为 |
| --- | --- |
| 意图 LLM 超时/无效 | 一次受限修复后仍失败则错误/澄清，不生成伪成功 |
| 解释 LLM 失败 | 有效卡片 + 模板理由 |
| 语义服务失败 | 使用原候选与硬过滤并标记降级；语义要求无法满足时说明 |
| DeepFM 失败 | 语义和融合排序，标记降级 |
| Redis 失败 | PostgreSQL 恢复状态，降低缓存能力 |
| 索引不一致 | 禁用语义就绪状态，保留健康组件 |
| 无合法电影 | 明确无结果，提供可选调整建议 |
| 用户越权 | 拒绝访问，不能泄露会话内容 |

## 8. 部署与可观测性

LLM 凭据仅在后端环境变量，语义服务仅供内部网络调用。Compose 为语义服务增加健康检查、只读索引挂载和模型缓存挂载。模型下载与离线构建在独立阶段完成。

普通电影请求保持原超时；聊天客户端初始超时 25 秒，后端整体截止 20 秒。V1 使用普通 JSON 请求响应。

记录 request ID、用户/会话标识、模型标识、提示词版本、索引版本、动作、工具耗时、各阶段候选数、过滤原因、排序配置、降级原因、token 消耗。不记录 API key；公开报告脱敏，不提交用户原始聊天日志。

验收协议见[评估与验收](acceptance.md)。
